# Pull Request の作業を引き継ぐ

既存 PR を起点に目的と現在の実装を把握し、依頼された範囲の残作業を完了させる。Claude Code や Codex などの実行環境で利用できる機能を使い、調査・実装の進め方は対象に応じて選ぶ。元の会話履歴や特定の Issue workflow を前提にしない。

## 対象と作業範囲

指定された PR、または現在の branch に対応する open PR を対象とする。一意に特定できなければ利用者に尋ねる。closed / merged の PR は自動で再開したり、代わりの PR を作ったりしない。

PR 本文、関連する要件・設計、実際の差分、レビュー、最新 head の CI から、実装済みの内容と残作業を把握する。以前の完了報告やレビュー指摘は現在のコードと検証結果に照らして判断し、取得できない情報を「問題なし」と扱わない。

補足指示があればその範囲を優先する。「引き継いで進めて」という依頼なら、元の要件の未達、確認できる不具合、有効なレビュー指摘、変更に起因する CI 失敗に対応する。把握した目的と今回の対応範囲を短く共有し、要件から判断できない点だけ確認する。

## 作業場所

現在のセッションで作業するか、クラウドセッションへ委譲するかを依頼から決める。クラウドでの実行を依頼されたときだけ委譲し、判断できなければ確認する。

作業する branch は PR の head repository / branch とする。クラウドセッションなどで、環境が既定の作業 branch や push 先を指示していても、対象 PR の head branch を優先して checkout し、追加コミットも head repository の同じ branch へ push する。環境の表示や既定の PR 作成機能が別の branch を指したままになる場合は、そのずれを報告に含める。head branch へ push できない環境では、別 branch や新しい PR で代替せず、変更の所在と PR への反映に必要な操作を返す。

## クラウドへ委譲する場合

ローカルで対象 PR を特定し、PR が open であること、head branch が remote 上にありクラウドから取得できること、fork の場合は push できる見込みがあることを確認する。PR の head branch に対するローカルの未 push の変更は取りこぼさず、push が依頼範囲に含まれなければ起動前に確認する。PR の残作業の詳しい調査はクラウド側に任せてよい。

実行環境に組み込みのクラウド起動機能を使い、開始 branch を PR の head branch に指定する。利用可能な機能と指定方法は実行時にヘルプや公式資料で確認し、ローカルの遠隔操作をクラウド実行と混同しない。開始 branch を指定できない機能では、開始後に head branch を checkout させる指示で補う。

クラウド側にこの skill や元の会話があると仮定せず、次を含む自己完結した引き継ぎ文を渡す。

- PR URL と、push 先の head repository / branch。環境既定の branch ではなくここへ反映すること。
- 目的、依頼範囲（commit・push・PR 本文更新など）と終了条件。
- このセクション以外の本文の要点（作業範囲の把握、守ること、完了条件）。

起動後は同じ作業をローカルで重複して進めない。起動結果が不明なら実状態を確認してから再試行し、重複したセッションを作らない。

## セッションタイトル

対象 PR を特定したら、作業するセッションに PR 番号と作業内容が分かるタイトルを設定する。クラウドへ委譲する場合は委譲先のセッションが対象となる。例: `#123 認証エラーの修正`。利用者が指定したタイトルは尊重し、既に適切な名前なら保持する。

実行環境の正式な機能を使い、成功を確認してから設定済みと伝える。設定できなければ推奨タイトルを伝えて作業を続ける。保存された会話ファイルを直接書き換えたり、元の自動実装セッションを変更したりしない。

## 引き継ぎで守ること

- 対象 PR の最新 head を基に作業し、実際の base に対する変更を確認する。利用者の未コミット変更と既存の成果・履歴・contributor の attribution を保持する。作業場所は安全に再利用できる checkout または worktree を選ぶ。
- 元の自動実行が継続中という証拠や競合する更新があれば、同じ branch を同時に変更せず調整する。作成者が同じアカウントであることを、実行終了の根拠にしない。
- 範囲外の改善を混ぜず、引き継ぎだけを理由に Issue の担当者・label・自動実行設定を変更しない。
- commit・push・PR 本文更新は利用者の依頼範囲に従う。「修正して PR を更新」にはこれらを含む。公開範囲が判断できなければローカルで実装・検証を進め、具体的な成果を示して確認する。既に許可された操作は再確認しない。
- 公開する場合は同じ PR の head repository / branch に追加コミットを反映し、force push や履歴の書き換えを既定の手段にしない。更新直前に PR の状態と head を確認し、他の変更があれば整合させて必要な検証をやり直す。更新結果が不明なら実状態を確認してから再試行する。
- PR 本文を更新するときは、要件・関連 Issue・close キーワード・他者の記載を保持し、最終的な変更と検証結果に整える。重複 PR は作成しない。
- レビューへの返信や resolve、draft 解除、merge、継続監視などは依頼に含まれる場合に扱う。

## 完了条件

依頼範囲の変更を実装し、PR 全体との整合性を確認する。変更に応じた検証と repository の必須チェックを行い、今回の変更による失敗は修正する。外部要因による失敗や未検証事項は成功と区別する。変更が不要な指摘には根拠を示す。

PR 更新まで依頼された場合は、意図したコミットが既存 PR に反映されたことを確認する。以前の head の CI 成功を現在の結果として扱わない。

PR URL、変更の要点、検証結果、commit / push の状況、残った懸念を返す。中断時は変更の所在、blocker、再開に必要な情報を残す。

クラウドへ委譲した場合は、意図したセッションが作業を受け付けたことを確認し、確認できる範囲で開始 branch が PR の head branch であることも確かめる。委譲先の URL / ID、開始 branch、PR への反映方法、残っている手動操作を返す。起動しただけの状態を PR 更新済みと扱わず、委譲先の完了の監視は依頼された場合に行う。
