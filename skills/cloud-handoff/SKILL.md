# ローカルの作業をクラウドへ引き継ぐ

クラウド側が元の会話を読めなくても、正しいコードと判断材料から残作業を再開できる状態にする。引き継ぎ準備だけか、クラウドでの実行開始までかを利用者の依頼から判断し、移送方法は実行環境の正式な機能に合わせて選ぶ。

## 引き継ぎ先と作業状態

現在の会話と repository から、引き継ぐ目的、作業範囲、コードの状態を把握する。移行先のサービス・repository・環境は利用者の指定と既存の設定を優先し、一意に決められない点だけ確認する。Claude Code と Codex の間でも、会話履歴の互換性や同じツールの存在を前提にしない。

ローカルの遠隔操作と、ローカルを終了しても続くクラウド実行を区別する。利用可能な機能や転送対象が不明なら、その環境のヘルプ・ツール定義・公式資料を確認する。クラウド移行に対応しない機能を、名前が似ているという理由で代用しない。

## 引き継ぐ内容

次の作業者が必要とする情報を、短く自己完結した引き継ぎ文にまとめる。項目や書式は作業に合わせて選び、会話全体の転記や不要な経緯は含めない。

- 達成したい成果、受入条件、利用者の制約、既に決まった設計とその理由。
- repository、開始する branch と commit、関連 Issue / PR、実装済みの内容と未完了の変更。
- 残作業、次に着手する箇所、未解決の判断や blocker。
- 実施済みの検証とその対象・結果、未実施の検証、再現に必要な環境やコマンド。
- クラウド側に任せる操作の範囲と終了条件。commit・push・PR 作成・既存 PR 更新などは、利用者が依頼した範囲を引き継ぐ。

秘密情報の値やローカル固有の絶対パスを前提にせず、必要な環境設定と入手方法を記す。ローカル専用の依存物やアクセス権が不足する場合は、クラウド側で実行可能な作業と不足する前提を区別する。引き継ぎ文は転送するコードの状態と一致させる。

## コードと文脈の受け渡し

未コミット・未追跡・未 push の変更のうち、作業の継続に必要なものを確認する。正式な移送機能、到達可能な remote branch、対応する添付などを使い、引き継ぎ文と必要なコードの両方がクラウド側へ届く方法を選ぶ。ローカルのファイルパスを伝えただけでは転送済みと扱わない。

利用者がクラウドへの引き継ぎ実行を依頼した場合は、そのために必要な対象変更の commit・既存の作業用 remote への push・セッション起動を含めて進める。「準備だけ」「push しない」等の指定は優先する。無関係な変更や秘密情報を混ぜず、ローカルの変更と既存履歴を保持する。転送範囲や公開先が判断できない場合は、引き継ぎ内容を用意してから必要な点を確認する。

対応する移送機能があれば使い、なければ引き継ぎ文を渡したクラウドセッションを作成する。既存セッションを指定された場合はそれを対象とする。起動結果が不明なら確認してから再試行し、重複実行を避ける。自動で起動できない場合は、そのまま使える引き継ぎ文と必要な手動操作を利用者へ返す。引き継ぎのためだけに新しい PR や Issue を作成する必要はない。

受け渡し後は、ローカルとクラウドで同じ作業を重複して進めない。進行中の処理があれば競合しない区切りを設け、元のセッションや worktree を自動で削除・アーカイブしない。引き継ぎ先のタイトルは作業内容が分かる名前とし、PR があれば番号も含める。

## 完了条件

準備の完了には、クラウド側が取得できるコードの所在、自己完結した引き継ぎ文、残っている手動操作が明らかであることが必要となる。実行開始まで依頼された場合は、さらに意図したクラウドセッションが引き継ぎ内容を受け付けたことを確認する。確認できる範囲で開始地点やセットアップ状態も確かめ、投入済みと実行可能・実行中を区別する。

引き継ぎ先の URL / ID、渡した branch / commit または snapshot、作業範囲、転送できなかったもの、現在の状態を簡潔に返す。準備のみ・起動待ち・起動失敗を引き継ぎ完了と報告しない。クラウドでの実装完了の監視は、別途依頼されている場合に行う。
