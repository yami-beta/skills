# 要件ごとの管理ボード

管理ボードは親要件ごとに用意する。「状況を更新」は管理セッションで GitHub と子の状態を読み直す操作。「同じ子に追加指示」は対象の task / PR と利用者の指示文を管理セッションに渡す操作。元の管理会話に依頼が届いたことと、担当の子から返信が届いたことは別々に確認する。

## Claude Code の管理セッション

1. 初回は親要件の管理ボードを非公開の Artifact として作成する。タイトルにリポジトリ名と要件番号を入れ、返された URL をこの会話に記録する。後からは元の管理セッションを再開し、記録した URL または `/artifacts` からボードを開く。
2. ボードの各 task / PR 行に、指示文の入力欄と送信ボタンを置く。送信ボタンを押すと宛先の task / PR と指示文を表示し、利用者が確認してから送る。公開時は `capabilities` に `db` と `user`、`mcp` の `Claude Code Remote` コネクタの `send_message` を宣言し、通知先として管理セッションの session ID をボードに持たせる。
3. 送信すると、ボードは `db` の `requests/<id>` に宛先 task / PR、指示文、送信者（`user.id()`）、作成時刻、状態 `pending` を記録する。記録できたら `send_message` で管理セッションに依頼 ID を添えて新着を知らせる。依頼 ID は送信ごとに一度だけ作り、通知を再試行しても同じ ID を使う。ボードは `requests` を購読し、各行に依頼の状態を表示する。
4. 管理セッションは通知を受けたとき、または利用者に促されたときに、`ArtifactData` で `requests` から `pending` の依頼を読む。宛先を担当の記録と GitHub に照合し、同じ子に依頼 ID を添えて指示を転送する。結果は同じ依頼に書き戻す。
   - `sent`: 子が指示を受け付けた。
   - `replied`: 同じ子から今回の指示への返信が届いた。返信の要旨を添える。
   - `failed`: 担当を特定できない、子がアーカイブ済み、送信を拒否されたなどで転送できない。理由を添える。

   転送するのは状態が `pending` の依頼だけとし、`sent` / `replied` / `failed` の依頼は再び転送しない。転送の成否が不明な場合は、状態を変える前に子の履歴で依頼 ID の到達を確認し、届いていれば `sent` にして再送しない。
5. 閲覧者の環境で `send_message` が `listTools()` にない、拒否された、または失敗した場合も、`requests/<id>` の記録は残す。ボードはその行に管理セッションへ通知できなかったことを表示し、利用者は管理会話で「ボードの依頼を処理して」と促す。管理セッションは手順 4 と同じく `pending` を処理する。
6. `db` も使えない（`claude.use("db")` が `null`、または書き込みを拒否された）場合は、送信ボタンを使わず従来の手段に戻る。管理セッションが Artifact のコメントを受け取れる環境では、対象の行に「状況を更新」または「PR 番号・同じ子への追加指示」を書き、**Send to Claude** で送る。コメント送信も使えない環境では、対象と指示文をコピーできるようにして元の管理会話に貼り付ける。受付が不明な場合は貼り付ける前に会話の履歴を確認する。
7. `db` への記録や通知の成功は、管理会話への到達や子からの返信を意味しない。管理セッションが依頼を読んだこと、子が受け付けたこと（`sent`）、子が返信したこと（`replied`）をそれぞれ確認する。確認した子の状態や返信は管理セッションが `db` とボードに反映する。再公開すると同じ URL で更新を確認できる。[Claude Code の Artifacts 公式手順](https://code.claude.com/docs/en/artifacts)

## Codex デスクトップの管理チャット

Codex は利用環境と利用者の希望に合わせて管理ボードの実現方法を選ぶ。後からボードを開いて進捗を確認し、対象の task / PR を選んで、同じ管理チャット経由で担当の子に追加指示を出せるようにする。作成後は、再び開く方法と指示の出し方を利用者に伝える。
